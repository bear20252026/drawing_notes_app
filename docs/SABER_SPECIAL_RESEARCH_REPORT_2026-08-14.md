# Saber 专题源码研究报告：面向高品质手写笔记与绘图应用的架构学习

**研究对象：** [Saber](https://github.com/saber-notes/saber)  
**源码审阅基线：** `f534abb3a29ad9fa15d7bb83a5b69593477cda6c`（main 分支，研究时取得）  
**研究目标：** 识别 Saber 中真正带来 GoodNotes 类体验的架构与功能，并为现有 Flutter 绘图笔记应用给出可合规实施的学习路线。  
**结论摘要：** Saber 是值得深度学习的全平台手写笔记项目，但它的主仓库和 SBN 文件格式包均采用 **GNU GPL v3**。因此，若当前应用仍希望保持闭源或非 GPL 商业发行，**不能直接复制、粘贴、链接或以派生方式合入 Saber 的源码**；应学习其产品机制与架构思路，再以独立表达方式重写。若未来决定将整个应用以 GPLv3 发布并履行完整源代码与通知义务，才可评估合规源码复用。[1]

> Saber 的真正优势不在于“工具图标多”，而在于把输入仲裁、笔画质量、文档迁移、文件变更、同步、导出和自动保存串成可完成且可恢复的完整任务链。

## 1. 产品定位与成熟功能

Saber 是一个面向手写的跨平台 Flutter 笔记应用，官网公开提供 Android、iOS、Windows、Linux 等下载入口。其功能说明明确强调端到端加密同步、跨设备编辑、不重复叠色的高亮笔、无限层级文件夹、最近笔记以及会同步改变纸张的深色模式。[2] 这些能力并非仅停留在宣传页；源码中能分别找到手写渲染、文件管理、同步和导出实现。

| 成熟能力 | 源码/产品证据 | 为什么用户会真实感到“好用” | 对现有项目的启发 |
| --- | --- | --- | --- |
| 低延迟手写 | 笔画有低/高两种质量缓存；书写中稀疏采样，收笔后全质量重建 | 写字时不卡顿，停笔后边缘平滑 | 用渲染质量策略提升现有笔画体验，而不是先堆更多笔刷 |
| 压感与设备区分 | Stylus/InvertedStylus 专用归一化，悬停与侧键检测 | 用户能明确感知到“这是笔输入，不是鼠标模拟” | 将现有压感诊断扩展成输入仲裁器 |
| 高亮笔可读性 | 高亮笔先按颜色分层绘制，使用混合模式防叠色；普通笔画随后绘制 | 反复划线不变脏，书写和文字始终可见 | 这是可立即实施、效果最明显的 P1 改造 |
| 混排文档 | 单页聚合手写、图片、富文本、背景图、页尺寸和页面缩略图裁切 | 课程资料、手写和图片能处于同一页面，不是彼此割裂的功能 | 现有混排模型要优先补齐完整历史与统一导出 |
| 稳定文件演进 | SBN 格式版本号、迁移器、独立资源文件、SBA ZIP 归档 | 升级应用后旧笔记仍可打开；大文件不会拖死界面 | 建立版本头、迁移器和资源清单，而非频繁破坏 JSON 格式 |
| 离线文件库 | 递归目录、文件监听、最近访问、重命名/移动/删除/导出变更流 | 用户把笔记视为可管理的资料，而不是一堆卡片 | 笔记库应成为“文件操作中心”，不是只显示网格 |
| PDF 批注工作流 | PDF 在导入入口获得能力预检，按页面进入编辑；导出采用混合策略 | 文档批注可导入、书写、保存和交付 | PDF 批注值得作为当前产品最高价值的资料型工作流 |
| 加密同步 | WebDAV/Nextcloud 同步的文件与路径加密、后台加解密、删除防重 | 用户可跨端使用，并知道服务器不直接读取内容 | 同步只能在本地数据可靠后建设，不能先放“云同步”开关 |

## 2. 最值得学习的八个架构模式

### 2.1 笔画不是单一路径，而是“原始采样 + 几何缓存 + 完成态优化”

`Stroke` 同时保留点序列、压力、工具类型和笔刷参数，并延迟生成低/高质量多边形与 Path。书写阶段使用低质量策略：每隔若干点采样、关闭平滑与流线；完成笔画后才用全点生成高质量形状，并压缩相距过近的点。[3] 这比“每个指针移动事件立即做完整曲线重建”更适合高频压感输入。

现有应用已有 `StrokeRenderer` 和压力策略，因此不需要更换整个绘图内核。优先独立重写一个 `StrokeGeometryCache`：它不修改原始笔画模型，只按笔画状态和视图缩放维护预览路径、完成路径与失效标记。验收应包括长笔画、快速书写、极细笔、单点笔画、橡皮擦以及连续缩放的帧时间。

### 2.2 输入仲裁器比“兼容更多设备”更重要

Saber 先判断设备类型：只有 `stylus` 与 `invertedStylus` 才从 `pressureMin/pressureMax` 得到正规化压力；无有效范围的压感被标记为空。它还处理悬停、笔侧键和倒置笔，且在检测到触控笔后可关闭手指绘画。[4] 编辑器在手势开始时再结合指针数量、当前工具、选中页面和手指绘画设置决定这是不是墨迹；若单指书写切换为双指缩放，会撤回意外新建的一笔。[5]

这是一条极为关键的产品规则：**笔负责墨迹，手指默认负责视图，双指始终负责缩放；鼠标是可解释的桌面回退。** 当前应用已具备压力来源状态栏和部分手型工具，但仍应把这些分支集中到 `EditorInputArbiter`，避免 `EditorPage` 内多处条件互相冲突。

### 2.3 高亮笔必须是一种特殊渲染语义

Saber 不是简单把半透明黄色 Path 画到画布上。它先把高亮笔按颜色分组放入 `saveLayer`，使用 `BlendMode.darken`（深色主题改为 `lighten`）合成，再绘制普通笔画。这样同色高亮反复覆盖不会越来越暗，也能让后写的普通墨迹和文本保持清晰。[6]

这套逻辑对当前产品可独立重写，且不需要引入 GPL 代码。建议先限定为固定宽度、无压感高亮笔：选择颜色、绘制重叠笔画、切换深浅主题、导出 PNG/PDF 均应得到稳定视觉结果。实现上应只在同色高亮存在时创建局部 `saveLayer`，避免整页模糊/离屏层造成性能损耗。

### 2.4 历史记录服务于“可恢复编辑”，不是只做撤销按钮

Saber 的 `EditorHistory` 保存过去/未来操作栈、上次保存的操作标识、有限历史上限和“暂不清空重做分支”的状态。后者让它能够在判断某次笔画是双指缩放误触后安全移除刚记录的操作。[7] 历史项还包含绘制、擦除、移动、插入/删除页、文本变更、颜色变更和背景变更等有语义的动作。

现有应用应优先将撤销、版本恢复和自动保存统一在一个“操作日志 + 保存点”模型中。已经实现的完整页面版本快照是良好基础；下一步不是无限增加历史容量，而是让每一种页面元素操作都有可逆命令，并确保保存状态由历史服务而不是 UI 标志判断。

### 2.5 文件格式演进要在数据损坏发生前设计

Saber 的 `EditorCoreInfo` 记录 SBN 格式版本，并明确列出每个版本的迁移原因；图像从内嵌数据变为分离资源，SBA 归档则用 ZIP 打包 BSON 主文件与资源。文件较大时载入转入 isolate；加载失败在非调试构建中以只读/损坏状态降级，而不是崩溃。[8]

当前项目使用 JSON 和本地文件已能工作，但应该先补充三层设计：版本头、纯函数迁移器、资源清单。每个未来结构调整都只增加新的迁移步骤，绝不在 UI 内“顺手修正旧数据”。超过设定大小的图片和文档解析应在 isolate/background 任务中运行，避免笔记库滚动与编辑器首开掉帧。

### 2.6 导出必须按内容能力分层

Saber 的 PDF 导出没有声称“所有内容完全矢量”。它将高亮笔与铅笔视为需要光栅化的内容，同时用截图生成稳定背景，再将普通笔画/形状以矢量路径叠加到 PDF；图片预载、导出主题固定为浅色、并发数受 CPU 核数限制。[9] 这是非常成熟的工程选择。

现有应用已有 PNG/SVG/PDF/JSON/PPTX/Markdown 导出，下一阶段应建设统一 `ExportSnapshot`：冻结当前页面、预载资源、记录导出主题与目标尺寸，并明确每种对象是矢量、光栅还是不支持。只有这样，用户才能在深色模式、含图片和高亮笔的文档中得到与编辑器一致的交付物。

### 2.7 笔记库是由文件变更流驱动的工作区

Saber 的 `FileManager` 负责文件名合法性、数据目录迁移、递归监听、读写重试、最近访问、路径转换以及同步上传入队。浏览页订阅文件变更流；目录变化后刷新数据，多选后显示重命名、移动、删除与导出等实际动作。[10] [11]

现有项目已经有收藏与最近使用，应继续向“统一资料库”推进：文件夹、标签、笔记本和单页排序都应由同一个存储服务输出变化流。这样导入、自动保存、云备份恢复和外部文件修改不会让首页、搜索和编辑器各自拥有不一致的状态。

### 2.8 同步必须以本地优先、加密和冲突策略为前提

Saber 的同步通过 WebDAV 维护本地和远端文件元数据，路径与内容均可加密，后台 worker 负责加解密，远端删除有本地删除记录避免反复处理，预览文件优先于主体文件同步。[12] 这让同步在网络失败、文件删除和大文件场景中仍有可解释的状态。

这不应被直接搬到当前应用：除了 GPL 边界外，账户、密钥生命周期、冲突提示、日志与支持流程都尚未建立。正确顺序是：先做本地历史可靠性和备份 ZIP；再做本地变更日志；最后才接入端到端加密同步。同步状态必须可以显示“等待上传、上传失败、冲突、已完成”，而不是仅有一个“同步中”图标。

## 3. Saber 与现有应用的对标结论

| 领域 | Saber 的成熟点 | 当前应用真实基础 | 差距判断 | 建议优先级 |
| --- | --- | --- | --- | --- |
| 手写笔体验 | 输入仲裁、双质量笔画、侧键/悬停、高亮语义 | 压感正规化、状态提示、基础笔画和擦除 | 可在现有基础上快速提升 | P0–P1 |
| 文档模型 | 多页、图片、富文本、PDF 背景、格式迁移 | 手写、文本、图片、形状、图表、连接线 | 已有更多对象类型，但需统一序列化/历史/导出 | P1 |
| 历史与保存 | 操作语义、保存点、误触回退 | 撤销/重做、版本快照已改善 | 需要操作日志服务化 | P1 |
| PDF 工作流 | 导入、逐页批注、混合 PDF 导出 | 有基础导出，没有完整逐页 PDF 批注 | 对知识工作用户的最大缺口 | P1 |
| 笔记库 | 目录树、最近项目、变更流、多选管理 | 收藏、最近、模板、笔记本视图 | 需要资料库统一索引与批量操作 | P1 |
| 导出质量 | PDF 混合策略、资源预载、稳定主题 | 多格式导出已有 | 需要导出快照与内容能力矩阵 | P1 |
| 同步隐私 | 端到端加密 WebDAV、后台任务、删除策略 | 本地加密和密码盘 | 必须经过本地优先基础设施后再做 | P2 |
| 国际化与平台支持 | 多语言、Windows/iOS/Android/Linux/macOS | Windows/Android 为主、简体中文体验优化中 | 先完善中文/英文与键鼠/笔输入，再扩平台 | P2 |

## 4. 合规复用策略

| 选项 | 是否推荐 | 结果 |
| --- | --- | --- |
| 复制 Saber 的 Dart 文件、Widget、渲染器或 SBN 包进入当前应用 | **不推荐，除非整体项目转 GPLv3** | 会触发 GPLv3 的派生作品、许可证与相应源代码义务；需专业法务确认 |
| 引入 Saber 仓库或 SBN 包为直接依赖 | **不推荐，除非整体项目转 GPLv3** | 即使是小型内部包，仍应按 GPLv3 的合规要求处理 |
| 阅读 Saber 代码后，独立重写“高亮分层”“输入仲裁”“操作保存点”等理念 | **推荐** | 功能思想和一般性算法可学习；必须避免逐行改写、复制独特结构/注释/命名，并保留独立设计记录 |
| 使用具有独立宽松许可证的第三方基础库 | **可评估** | 需逐一核验库及其依赖的许可证，例如笔画生成、加密、PDF、文件选择器等 |
| 将当前应用明确发布为 GPLv3 开源产品 | **可选战略决策** | 可考虑代码复用，但须补齐源码发布、版权归属、许可证文本、修改说明、依赖清单与安装信息；建议先取得法律意见 |

> 本报告是工程与许可证文本阅读结论，不构成法律意见。若计划公开发布、商业销售、接入闭源云服务或直接复制 GPL 代码，应在发布前取得合格法律顾问的书面判断。

## 5. 推荐的 90 天实施路线

| 阶段 | 目标 | 必须交付的真实功能 | 验收标准 |
| --- | --- | --- | --- |
| 第 1–2 周：书写质量 | 让笔、手、鼠标各司其职 | `EditorInputArbiter`、压力校准页、掌托策略、双质量路径缓存 | Windows/Android 各至少两种笔硬件；书写、手掌、双指缩放和侧键互不误触 |
| 第 3–4 周：高亮与导出 | 让资料批注看起来像成熟笔记工具 | 分层不叠色高亮笔、导出快照、资源预载、PNG/PDF 一致性测试 | 反复划同色不变黑；深/浅模式导出页面一致；含图片页面不丢资源 |
| 第 5–7 周：PDF 批注 | 建立高价值资料工作流 | PDF 选页导入、背景资源、每页批注层、再打开、PDF 导出 | 10 页 PDF 导入、书写、关闭、重开、导出完整；原文件不被修改 |
| 第 8–10 周：资料库与历史 | 让用户可管理、敢修改 | 文件夹/标签/批量整理、统一变更流、操作日志与完整恢复 | 恢复后所有对象一致；导入/移动/删除后主页与搜索同步更新 |
| 第 11–13 周：本地备份与同步预研 | 为跨端能力建可靠底座 | 可验证 ZIP 备份/恢复、冲突模型、密钥生命周期设计、同步状态原型 | 断网/重复恢复/冲突模拟不丢数据；尚未达到条件时不开放同步开关 |

## 6. 最终建议

Saber 值得作为本项目的**工程标杆**，尤其适合学习三件事：第一，把低延迟手写建立在输入仲裁和双质量渲染上；第二，把笔记保存、历史、文件库和导出当作同一文档系统；第三，任何高级功能都只在“导入—编辑—保存—重开—导出/恢复”的闭环可验证后才暴露给用户。

对当前项目而言，下一次大范围改造不应从“再加一个新工具”开始，而应从**触控笔输入仲裁 + 不叠色高亮笔 + 导出快照 + PDF 批注基础模型**开始。这四项会立即让用户感到书写更顺、资料更好用、导出更可信，同时不会破坏您已经形成的苹果式玻璃控制层与内容优先布局。
